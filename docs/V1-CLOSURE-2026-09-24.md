Service worker global y manifest dinámico por tarjeta. Checkout Pro de Mercado Pago, Resend para avisos, pg_cron y pg_net. QR por QuickChart; Supabase JS desde jsDelivr; imágenes externas en las demos.

## Pruebas reproducibles

- `node --test tests/*.test.cjs`: 21 pruebas. Node 22 actualizado o 24, por `stripTypeScriptTypes`.
- Se ejecutaron los 17 pasos run de QA Gate y Security Gate localmente: todos pasaron antes del último ajuste de caché/métricas; CI debe confirmar el conjunto final.
- `tests/database-rollback.sql`: 15 comprobaciones de funciones y roles reales, con usuarios/tarjetas/pagos sintéticos dentro de BEGIN/ROLLBACK. No envía correos ni llama a Mercado Pago. El procesador de vencimiento puede bloquear temporalmente filas vencidas durante esta transacción y luego revierte; ejecutar en ventana controlada. Las secuencias de eventos pueden dejar huecos aunque los datos se reviertan.
- Para validar antes de desplegar: insertar el contenido de la migración después de BEGIN en la prueba SQL. Se ejecutó así y los 15 resultados fueron true.
- El script SQL devuelve booleanos: cualquier false debe detener la liberación; no basta el código HTTP 200.
- Pruebas de mocks no validan credenciales reales ni entrega de proveedores.

## Seguridad y deuda operativa

Las ocho tablas públicas tienen RLS; `apply_verified_payment_gateway` sólo permite service_role. Bucket público `profile-assets`: máximo 12 MB; MIME JPEG/PNG/WebP/MP3/PDF; escritura restringida a carpeta del usuario. La clave publicada es publishable, no service_role. Security Gate no detectó secretos de alto riesgo; no es una auditoría completa de todo el historial Git.

Supabase Advisor advierte protección de contraseñas filtradas desactivada: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection

El índice de una tarjeta contiene excepciones para `pablogarza`, `prueba-automatica-3506001`, `prueba-produccion-180926`, `beta2-laboratorio`. No retirar esas excepciones sin reconciliar registros y cuentas. Existe código de login duplicado y dos triggers de protección de perfiles; no eliminarlos sin probar acceso real.

`supabase/schema.sql` y los SQL históricos NO reproducen por sí solos la base actual. Faltan cambios posteriores y contienen reglas de prueba/vencimiento anteriores. La migración de este cierre es incremental sobre producción auditada, no un baseline para una base vacía. Recuperación debe partir de backup nativo verificado; quedan pendientes ensayo de restore y respaldo de objetos Storage.

La idempotencia de Resend cubre 24 horas; notification_log conserva la deduplicación permanente. Ver documentación: https://resend.com/docs/dashboard/emails/idempotency-keys. No se promete exactly-once indefinido si fallan tanto el log como los reintentos más allá de esa ventana.

## Puerta de lanzamiento y prueba real

P0 pendiente de cierre comercial: validar cuenta real, publicación persistente y pago real controlado con retorno/webhook/plan activo. Ningún test autoriza por sí solo declarar la V1 vendida o certificada.

1. Usar correo de prueba controlado, completar registro y confirmación, login, guardar y publicar una tarjeta; cerrar sesión y comprobar persistencia al entrar de nuevo.
2. Abrir `/crear/` con esa cuenta; seleccionar Personal y verificar $399 MXN/año. Preparar checkout una sola vez; comprobar merchant, importe y ambiente de producción.
3. Detener automatización antes de ingresar instrumento de pago o confirmar cobro. El usuario ejecuta el pago real.
4. Verificar orden/pago aprobados en Mercado Pago, retorno y webhook. En Supabase verificar un solo provider_payment_id, status approved, subscription_plan personal y vigencia anual.
5. Refrescar y repetir confirmación sin extender nuevamente; abrir tarjeta en incógnito, compartir/QR e instalación; verificar eventos.
6. Validar renovación con casos sintéticos ya disponibles y aviso a correo autorizado. La entrega real del aviso requiere revisar bandeja/spam y logs del proveedor.

P1: entrega real Resend; recuperación de contraseña; autenticación móvil; instalación nativa; restore de backup; concurrencia avanzada de pagos/reembolsos y prevención de dos checkouts desde pestañas distintas.

P2: consolidar login/triggers históricos y código de demos, fijar dependencias CDN a versión exacta, retirar lógica obsoleta tras validar compatibilidad. Congelación de funciones vigente.
